# Feature Specification: Prompt Runner

**Feature Branch**: `001-simple-prompt-runner`

**Created**: 2026-11-01

**Status**: Implemented (User Stories 1–11); the live check with the user's own API key is left to the user

**Input**: User description (latest, replaces the earlier step-by-step descriptions): "1) Powinnismy zaczać od 'Nowa Sesja'. 2) Najpierw ładujemy prompt, w ustalonym formacie: ID, nazwa, prompt-input, expected results (żeby uprościć wrzucimy dokładny tekst). 3) Następnie dostosowujemy main prompt. Widzimy main prompt z miejscem na wprowadzenie {prompt_input}, pod spodem przykładowy całkowity prompt. 4) Mamy dwa judge, accuracy i completeness. Prompty będą musiały używać {prompt input} i output z main promptu żeby porównać wyniki. Wyniki będą zwracane w formie rationale i procentu. 5) Pod spodem widzimy konfigurację. Możemy podać endpointy i klucze API. Na razie nie dajemy dodatkowych opcji. Osobne dla Main promptu i LLMasJ. 6) W momencie uruchomienia: uruchamiamy main prompt, a potem LLMasJ. Wyświetlamy wynik w HTML: u góry (main prompt i Judge) - celem archiwizacji; każdy wynik: ID, scenariusz, prompt input, actual output, similarity to expected output (%), Accuracy - Grade, Accuracy - Rationale, Completeness - Grade, Completeness - Rationale."

**Scope**: This is the single specification of the application. It is deliberately minimal: one page that is filled in from top to bottom, request parameters only as one optional JSON text per model, no judge versions, no list of endpoints, no run comparison, no manual entry. The app runs locally on the user's own computer (a hosted version for several people is a later step and out of scope). Anything not described here is out of scope.

## Overview of the page

After the user presses **New Session**, one page is filled in from top to bottom:

1. **Dataset** – loaded in a fixed format (ID, name, prompt input, expected result).
2. **Main prompt** – editable text with a place for `{prompt_input}`, and below it an example of the complete prompt.
3. **Two judges** – Accuracy and Completeness, each with its own prompt that uses `{prompt_input}` and `{output}`.
4. **Configuration** – for the main prompt: an endpoint, an API key, and one JSON field that holds the model and its parameters. The judges use the same model by default; their own fields appear only when the user switches that off.
5. **Run** – the main prompt runs on every selected row (all rows by default), then the judges; failed rows can be re-run afterwards.
6. **Result** – an HTML report: the prompts used at the top (for archiving), then one block per row.

The whole page, not only the report, has the modern look of FR-048: a header band with the facts of the session, a step indicator, cards per step, and a run panel with a live readiness list.

## Clarifications

### Session 2026-11-01

- Q: When some rows fail (for example because of the platform's rate limit), should the user be able to re-run only the failed rows, or choose which rows to run? → A: Both: the user chooses the rows to run before a run, and can re-run the failed rows after it.
- Q: How should the app compute the similarity to the expected output? → A: Character-level similarity (edit distance): the number of single-character changes needed to turn one text into the other, relative to the longer text.
- Q: What is the largest number of rows a single run must handle? → A: Up to 20 rows per run.
- Q: Where should the app run: locally on the user's computer, or as a hosted page for many people? → A: Locally on the user's computer first; a hosted version is a later step and out of scope for this version.
- Q: In which language should the interface, its messages, and the report labels be? → A: Everything in English, including the start button ("New Session"); the original Polish wording of the first request is kept only in the Input line.

### Session 2026-11-01 (report layout, after the first real runs)

- Q: How should the results of several countries be laid out so that two can be read next to each other? → A: One table with every test case (country) in its own line, one under the other, never as columns (a first proposal with one column per country was rejected because it breaks down with many countries). Each test case takes two lines: the main prompt line (prompt input, expected result, actual output, similarity, differences side by side) and below it the judge line (the metrics one under another, each with its grade and rationale).
- Q: How should the differences between the expected result and the actual output be shown? → A: One text, compared by words: words only in the expected result struck through, words only in the actual output marked as added.
- Q: What happens to the former block of ten fields per row? → A: It is replaced by the table of test cases described above; the archive no longer repeats the model and parameters JSON, which are in the prompts table.
- Q: How should the long prompt input be shown, since a collapsible text looks odd? → A: As its own wide column of the main prompt line, in a box of limited height that scrolls inside itself (always visible, never collapsed, with its length in characters); the report uses the full width of the page. (A separate full-width line for the prompt input was tried first and replaced by the column.)
- Q: Which appearance should the report have? → A: The modern, professional appearance of the reference `example-report-modern.html` (header band, cards with the averages as ring gauges, bars and badges in the summary table, cards per test case, light and dark following the system). It applies to the report only; the application page keeps its current look (the restyle of the page was specified separately afterwards: User Story 9).
- Q: How should the full-width report fit into the page, whose steps 1–4 are a narrow column? → A: The report opens in its own full-width view that replaces the steps (opened automatically when a run finishes or is stopped, and with an "Open report" button at any time), with a toolbar holding "Back to the form", "Export HTML", and "Export CSV"; the form keeps all its content. (Two other options were considered: the report widening out of the column in step 5, and a full-width page for everything.)
- Q: Can a re-run repeat only the requests that failed, not all of them? → A: Yes, that is what "Re-run failed requests" (formerly "Re-run failed rows") does: it sends only the requests that ended with an error or were not run (a main request for a row without an output, a judge request without a valid grade); with two rows and one failed judge request, exactly that one request is sent. Its confirmation lists every request on its own line, and the confirmation of "Re-run judges only" points to it. ("Re-run judges only" itself still repeats all judges, on purpose, after a judge prompt was edited.)
- Q: When a judge prompt was corrected after an unreadable answer, which prompt should "Re-run failed requests" use for the judge requests, given that successful requests must not be repeated? → A: The current text of the judge prompts (model and parameters stay archived); the grades that succeeded earlier are kept, and the report notes how many grades come from an earlier version of a judge prompt and keeps that version in the archive. The main prompt stays the archived one.
- Q: What should the main prompt line (five fields side by side) do on a narrow window, for example a phone or half a screen? → A: Below about 900 px of window width the fields of one test case are shown one under the other, each across the full width with its own label; above it they stay side by side. The report is never wider than the window.
- Q: Do the other long texts (expected result, actual output, differences, rationales) get the same kind of box as the prompt input? → A: Yes: every long text is shown in full in a box of limited height that scrolls inside itself (about 17 lines for the fields of the main prompt line, about 9 lines for the rationales); short texts take only the space they need.

### Session 2026-11-02 (modern look of the application page)

- Q: Should the application page with the steps (dataset, prompts, judges, configuration, run) get the same modern, professional look as the report? → A: Yes. The page takes over the visual language of the report (header band, rounded cards with soft shadows, badges, ring gauges and bars, light and dark following the system) and gains a step indicator, a live readiness list, and chips with the key facts of the session. The user is open to negotiating the arrangement of the fields, the place of the buttons, and the animations; the proposal below (User Story 9, FR-048 – FR-057) was shown on the reference page [example-form-modern.html](example-form-modern.html).
- Q: Does the new look change what the application does? → A: No. Every behavior and every rule of FR-001 – FR-047 stays (consent before sending, locked form while confirming, keys in memory only, English only, nothing stored in the browser); only appearance, arrangement, and the added indicators change.
- Q: Is the reference page [example-form-modern.html](example-form-modern.html) accepted as the layout of the application page? → A: Yes ("the mock-up looks good"). That settles the three open points in favor of what the reference page shows: the run panel stands at the side on wide windows (not as a bar at the bottom), the step indicator is horizontal under the header band (not vertical at the side), and the motion is subtle (transitions of at most 250 ms, none with reduced motion).
- Q: What should the readiness list in the run panel show at the start of a session, when steps 2–4 are not unlocked yet? → A: All problems of all steps from the start, grouped by step, with the groups of steps that are not unlocked yet dimmed (option C): the user sees the whole road at once, and the items of locked steps cannot be pressed.
- Q: Where should Run stand on narrow windows, where the run panel comes after all the steps? → A: In a bar fixed to the bottom of the window (option A) that shows the state (problems or ready, progress, result) and the primary action; the full panel with the list of problems, the progress, and the confirmation stays after the steps and comes into view when needed.
- Q: Can the hand walk-through of the quickstart (tasks T105 and T123) be automated? → A: In its larger part, yes: one command runs the whole walk-through in a real browser driven with real pointer and keyboard input against the fake platform, downloads the exports for real, repeats the visual checks at the four widths in the light, the dark, and the reduced-motion setting, and gives a verdict per quickstart row with evidence (User Story 10, FR-058 – FR-065). Three things stay with a human on purpose and are listed as such in the report: the judgment whether the page looks as professional as the reference page, the usability check with a first-time user (SC-011, SC-032), and the live check with the user's own key (which stays a separate script). A passing run, together with a look at the gallery of screenshots that it prepares, replaces the hand walk-through for acceptance.
- Q: What happens with the three items that stay with a human after the automated walk-through? → A: The user's decision: (1) whether the page looks as professional as the reference page is judged by the implementer from the gallery of screenshots (the user trusts that judgment); (2) the usability check with a first-time user (SC-032) is waived; (3) the live check with the user's own key is done by the user, with real data, once the implementer has declared the system ready. The report still lists the three items and the run still gives no verdict for them (FR-065).
- Q: Must the exported files hold no "prompt text" (FR-061, scenario 5 of User Story 10)? → A: No, that wording was wrong. The HTML export holds the prompts used (FR-022) and both files the prompt input of the rows (FR-023, FR-026), so they cannot be free of prompt text. The privacy rule of the quickstart is: the exports hold no key, no endpoint, and no address of the relay; the log of the application's process holds no key and no prompt text. FR-061 and the scenario were corrected to say so.
- Q: Can the test that checks that the API key is not stored be automated? → A: Yes, and part of it already is (a scan of the code for browser storage, the key fields and the browser's storage lists after a run, the log of the application, the exports, and the run folder). What is missing is an **audit** that looks everywhere a key could be left behind and in every way a run can end: the browser's own profile on disk, the files that the run changed, the console and the network traffic, the addresses and the history of the page, the memory of the page and of the application's process, and the runs that failed, were stopped, were repeated, or were abandoned; it proves that it can see a key (planted copies are found) and shows how much it examined (User Story 11, FR-066 – FR-073).
- Q: What should happen when the platform repeats the API key in its own error message? → A: The key must not travel back to the page at all: the relay removes it from the platform's answer before passing the answer on (found by the first run of the audit, which saw it in the network traffic although the page hid it from the screen; FR-074, SC-041).
- Q: Should the key also be removed from the platform's answer when the platform repeats it in a form other than plain text or JSON? → A: Yes (the user's choice, option A): in every form of the whole key that the audit searches for (plain text, JSON-escaped, escaped for an address, base64), so that FR-074 and the audit (FR-069) describe the same thing; a bare piece of the key is not searched for in the answer.
- Q: How should the two re-run buttons be arranged (Re-run judges is visible while the run is in progress, Re-run failed requests only afterwards), and what should happen when 1 of 10 rows has a single failed judge request? → A: One re-run control, always at the same place and in the report too, with four choices (the user's list): re-run all (main prompts and judges), re-run failing main prompts and all related judges, re-run all judges, and re-run only the failing judges; each shows how many requests it would send, and a choice that has nothing to send is unavailable with a reason. For one failed judge request of ten rows, "re-run only the failing judges" sends that one request and nothing else (User Story 12, FR-075, FR-076). This also settles the future of "Re-run judges only": it stays, as "Re-run all judges".
- Q: What should New Session do after the run has started? → A: One New Session button, its own button outside the re-run control, is visible on every screen after the start (also in the report and during a run); pressing it, after the usual confirmation, removes the report and everything else of the session (User Story 12, FR-077).

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Start a new session and load the dataset (Priority: P1)

The app opens on a start screen with one action, **New Session**. After pressing it, the user loads the dataset (by choosing a file or pasting its text) in the fixed format. Each row is one test with four fields: **ID**, **name** (the scenario), **prompt_input** (the data that goes into the main prompt), and **expected_result** (the exact expected text). The app checks the data and shows a preview.

**Why this priority**: Nothing else can happen without a session and data. The remaining stories follow the same page in order.

**Independent Test**: Press New Session, load a valid dataset and see its rows previewed; load one without an `expected_result` column and see a specific error naming it.

**Acceptance Scenarios**:

1. **Given** the app has just been opened, **When** the user looks at the screen, **Then** the only action offered is New Session, together with a statement that everything in a session is kept in memory only and is lost when the session ends or the app is reloaded.
2. **Given** a new session, **When** the user loads data that has the columns `id`, `name`, `prompt_input`, and `expected_result` (names matched ignoring letter case), **Then** the app accepts it and shows a preview of the rows.
3. **Given** data that lacks a required column, **When** the user loads it, **Then** the app names exactly what is missing and the following steps stay unavailable.
4. **Given** data with an empty or duplicate ID, an empty name, or an empty prompt input, **When** the user loads it, **Then** the app reports the offending rows and allows no run.
5. **Given** a row with an empty expected result, **When** the data is checked, **Then** the row is flagged; it can still be run, and its similarity is shown as "no expected result".
6. **Given** unreadable, malformed, or empty data, **When** the user loads it, **Then** a specific, readable error is shown and no run is allowed.
6a. **Given** text copied from a spreadsheet (tab-separated), or a file separated by semicolons or commas, **When** the user loads it, **Then** the separator is recognized automatically, and values containing commas, quotes, or line breaks (quoted where the format requires it) arrive intact in the preview.
6b. **Given** a record whose number of columns differs from the header (for example, an unquoted value containing the separator), **When** the user loads the data, **Then** the app names the record and the likely cause, loads nothing, and the user can correct the text and load it again.
7. **Given** a very long, multi-line value (tens of thousands of characters), **When** the dataset is shown, **Then** it is shown shortened with its length, can be expanded, and is sent complete with its line breaks.
8. **Given** a session with a dataset or results, **When** the user presses New Session again, **Then** the app warns that unexported results will be lost, requires confirmation, and then starts empty.

### User Story 2 - Main prompt with a live example (Priority: P2)

The user sees the main prompt as an editable text with a place for the data, written as `{prompt_input}`. Directly below it, the app shows an example of the complete prompt: the main prompt with `{prompt_input}` replaced by the value of a row of the loaded dataset.

**Why this priority**: The user must see exactly what the model will receive before spending anything.

**Independent Test**: Write a main prompt containing `{prompt_input}`, and confirm that the example below shows the first row's value in that place; switch the row and see it change.

**Acceptance Scenarios**:

1. **Given** a loaded dataset, **When** the user views the main prompt, **Then** it shows an editable text with `{prompt_input}` highlighted inside the text (the braces stay visible, so it does not rely on color alone).
2. **Given** the main prompt, **When** the user looks below it, **Then** an example of the complete prompt is shown for the first row, with the inserted value highlighted, and the user can choose another row.
3. **Given** the user edits the main prompt, **When** they type, **Then** the example updates immediately.
4. **Given** a main prompt without `{prompt_input}`, **When** the user tries to run, **Then** the run is blocked with a message that the place for the data is missing.
5. **Given** any other word in curly braces (for example `{history}`), **When** the user views the prompt, **Then** it is flagged as unknown and the run is blocked until it is removed; a literal brace is written doubled (`{{` or `}}`).
6. **Given** `{prompt_input}` appears several times, **When** the prompt is built, **Then** every occurrence receives the same value.

### User Story 3 - Two judges: Accuracy and Completeness (Priority: P3)

Under the main prompt the user sees two judge prompts: **Accuracy** and **Completeness**. Each is an editable text, already filled with a ready-made version, and each uses two places: `{prompt_input}` (the data the main prompt was given) and `{output}` (what the main prompt returned). The judge compares the output with the input data: Accuracy asks whether the output is true to the data, Completeness asks how much of the data is covered. Each judge returns a **percentage** and a **rationale**.

**Why this priority**: This is the quality signal beyond the plain similarity to the expected text.

**Independent Test**: Open both judge prompts, see the ready-made texts with both places highlighted, remove `{output}` from one and see the run blocked with a message naming the missing place.

**Acceptance Scenarios**:

1. **Given** the page, **When** the user views the judges, **Then** two prompts are shown, Accuracy and Completeness, each already filled in with a ready-made QA prompt and editable.
2. **Given** a judge prompt, **When** the user views it, **Then** `{prompt_input}` and `{output}` are highlighted inside the text, and a preview below shows the complete judge input for a chosen row (with a clearly marked stand-in for the output before any exists).
3. **Given** a judge prompt that lacks `{prompt_input}` or `{output}`, or contains another word in curly braces, **When** the user tries to run, **Then** the run is blocked with a message naming the judge and the problem.
4. **Given** the judges, **When** they are called, **Then** the app itself tells each judge to answer with a percentage from 0 to 100 and a rationale, so the user does not have to write the answer format.
5. **Given** a judge answered, **When** the answer has no usable percentage, **Then** the row shows a readable "unreadable answer" error for that judge together with the raw text, and the row is left out of that judge's average.
6. **Given** the judges, **When** the user looks at the page, **Then** it states that the judges add two extra requests per row (one per judge) and may cost extra.
7. **Given** the ready-made Accuracy prompt, **When** the user reads it, **Then** it casts the judge as a QA reviewer who extracts every verifiable fact from the output, checks each against the input data only, gives each fact a verdict (correct, incorrect with the correct value, or unsupported), accepts rounding, does not penalise omissions, and reports the list of facts with their verdicts and an overall accuracy percentage.
8. **Given** the ready-made Completeness prompt, **When** the user reads it, **Then** it casts the judge as a QA reviewer who lists every fact of the input data, checks whether each appears in the output with the same value (a wrong value still counts as present, with a note), and reports the list of facts that appear, the list of facts that are missing, and an overall completeness percentage.
9. **Given** a judge answered, **When** the row is shown, **Then** the list of facts and their verdicts (for Accuracy) or the lists of appearing and missing facts (for Completeness) is part of that judge's rationale, so the user sees which facts match or appear and which do not.

### User Story 4 - Configuration: endpoint, one JSON for the model, and the judges' model (Priority: P4)

Below the prompts the user sees the configuration. The **Main prompt** block has three fields: an **endpoint** address (pre-filled with the test platform's address), an **API key**, and one text field with the **model and its parameters as a JSON object**. The model is named inside that JSON (the `model` key), so there is no separate model field. Under it, the **LLM as Judge** part has one option, **"Same model as the main prompt"**, which is **on by default**: the judges then use the same endpoint, key, and JSON as the main prompt, and no judge fields are shown. Only when the user switches the option off does the judge part show its own endpoint, API key, and JSON (pre-filled with the second known model), used by both judges. There are no other options.

**Why this priority**: Without it nothing can be sent, but it is a small form: two fields and a JSON, and the judges need nothing extra in the usual case.

**Independent Test**: Enter a key and run with the defaults; confirm that the main prompt and both judges use the same endpoint, key, and JSON. Switch the option off, fill the judge fields, and confirm that only the judges use them.

**Acceptance Scenarios**:

1. **Given** the page, **When** the user views the configuration, **Then** the Main prompt block shows an endpoint (pre-filled with the test platform's address), an API key, and a JSON field pre-filled with the default model and parameters; below it the option "Same model as the main prompt" is on and no judge fields are shown.
2. **Given** the option is on, **When** the user starts a run, **Then** every judge request goes to the main prompt's endpoint with the main key and the main JSON (the same model and parameters), and the user entered the key only once.
3. **Given** the user switches the option off, **When** they view the judge part, **Then** it shows its own endpoint, API key, and JSON field, pre-filled with the second known model, and both judges use them; switching the option on again hides the fields again and the judges go back to the main prompt's configuration.
4. **Given** a shown block whose endpoint is empty or not a well-formed http or https address, or whose key is empty, **When** the user tries to run, **Then** the run is blocked with a message naming the block and the field.
5. **Given** a shown JSON field that is empty, not valid JSON, not a JSON object, without a non-empty text under `model`, or containing the keys `messages` or `stream` (which the app sets itself), **When** the user tries to run, **Then** the run is blocked with a message naming the block and what is wrong (for example, the position of the JSON error).
6. **Given** a valid JSON, **When** a request is sent, **Then** the JSON is added to the request as written, without range checks; if the platform rejects it (unknown or not permitted model, unsupported parameter), the row shows a readable error that names the model and the parameters as the likely cause.
7. **Given** a key has been entered, **When** it is displayed, **Then** it is masked.
8. **Given** a run, a judge re-run, or a re-run of failed requests has finished, failed, or been aborted, **When** the user looks at the configuration, **Then** the keys are cleared and must be entered again for the next run; endpoints and JSON may stay while the session lasts.

### User Story 5 - Run and read the HTML report (Priority: P5)

When all inputs are complete, the user starts the run. The app first runs the main prompt on every selected row, then runs the judges on the outputs. The result is shown as an HTML report. At the very top it contains a summary table of all rows, a table of the prompts used with their models, parameters, and generation dates, and the prompts exactly as used (for archiving). Below it, every row has one block with: **ID**, **scenario** (the name), **prompt input**, **actual output**, **expected result**, **similarity to expected output (%)**, **Accuracy – Grade**, **Accuracy – Rationale**, **Completeness – Grade**, and **Completeness – Rationale**.

**Why this priority**: This is the result the user came for. It depends on the previous stories.

**Independent Test**: Run a dataset of three rows with both judges and confirm that the report shows the three prompts at the top and, for each row, a column with all the fields of FR-023.

**Acceptance Scenarios**:

1. **Given** all inputs are complete, **When** the user starts the run, **Then** the app first states how many requests will go to each endpoint and what data goes to each (the prompt with the input to the main endpoint; the input data and the output to the judge endpoint), and sends nothing until the user confirms.
2. **Given** a confirmed run, **When** it is in progress, **Then** the main prompt is run on every selected row first, and the judges only after that; progress is shown for each of the two phases.
3. **Given** a row, **When** the main prompt has answered, **Then** the actual output is shown, together with its similarity to the expected output as a percentage: computed by the app from the two texts without any model call, as the character-level similarity defined in FR-024 (100% when identical, lower the more characters differ).
4. **Given** a row, **When** a judge has answered, **Then** its grade (a percentage) and its rationale are shown in the row's block, labeled Accuracy or Completeness.
5. **Given** the report, **When** the user looks at its very top, **Then** it shows a compact summary table with one line per row of the run and the columns test case (ID and name), similarity (%), Accuracy score (%), and Completeness score (%), and a final line with the average of each score; the table of the prompts used (scenario 5b) and the prompts as used follow below it.
5a. **Given** the summary table, **When** a row failed, was not run, was not judged, or has no expected result, **Then** its line shows that state in place of the missing value instead of a blank, and the user can click the test case to jump to the lines of that row.
5b. **Given** the report, **When** the user looks right below the summary table, **Then** a second table lists the main prompt and each judge with the model used, the request parameters used (the JSON without the `model` key, shown as a short list of names and values), and the date and time at which that prompt's results were generated; the date and time at which the report was produced is shown above the tables.
5c. **Given** the judges were re-run, **When** the report is shown, **Then** the date and time of the judges is that of their latest run, while the date and time of the main prompt stays that of its run.
6. **Given** the report, **When** the user looks at the results table, **Then** every test case is shown in its own lines, one test case under the other, so that the table grows downward and never wider with more test cases: a heading line with the test case (ID and name); the main prompt line with prompt input (a wide column with a box that scrolls inside itself, not collapsed), expected result, actual output, similarity, and differences side by side; and the judge line below it, in which the metrics (Accuracy, Completeness) are one under the other, each with its grade and rationale. The differences show the words removed from the expected result as struck through and the words added by the model as marked.
7. **Given** the main prompt fails on a row (invalid key, rate limit, timeout, input too long), **When** the run continues, **Then** the row shows a readable error instead of an output, the judges are not called for it ("nothing to judge"), and other rows are unaffected.
8. **Given** a judge fails on a row, **When** the run continues, **Then** that judge's fields show a readable error, and the other judge and rows are unaffected.
9. **Given** a run in progress, **When** the user stops it, **Then** no further requests are sent, finished rows keep their results, and unfinished rows are marked "not run".

### User Story 6 - Re-run only the judges (Priority: P6)

After a run, the user edits a judge prompt and runs the judges again on the outputs the main prompt already returned. The main prompt is not called again, so the outputs stay exactly the same and any change in grade comes from the judges alone.

**Why this priority**: Judge prompts are rarely right the first time. Re-running only the judges saves cost and keeps the outputs fixed.

**Independent Test**: After a run, edit the Accuracy judge prompt, re-run the judges, and confirm that new Accuracy grades appear for the same outputs and the main endpoint received no request.

**Acceptance Scenarios**:

3. **Given** the re-run changed a grade, **When** the user looks at that row, **Then** the new grade replaces the old one and the previous grade is shown next to it.

### User Story 7 - Choose which rows to run and re-run the failed ones (Priority: P7)

Before a run, the dataset preview shows a check box for every row, all selected by default, so the user can run a subset (for example one country to try a prompt). After a run, when some rows failed, for example because the platform's rate limit was exceeded, the user can re-run only what is missing instead of repeating the whole run: the app completes the failed and not-run rows and leaves everything that already succeeded unchanged.

**Why this priority**: With a free request limit of about 40 a minute and three requests per row, failures on longer datasets are likely; this avoids repeating requests that already succeeded and keeps good results.

**Independent Test**: Run a dataset in which one row fails, use "re-run failed requests", and confirm that only that row's missing requests are sent and every other row is unchanged.

**Acceptance Scenarios**:

1. **Given** a loaded dataset, **When** the user views the preview, **Then** every row has a check box, all rows are selected by default (the first 20 when the dataset has more than 20 rows), there are "select all" and "select none" actions, and the number of selected rows is shown together with the limit of 20 per run.
2. **Given** no row is selected, or more than 20 rows are selected, **When** the user tries to run, **Then** the run is blocked with a message that between 1 and 20 rows are needed and how many are selected now.
3. **Given** some rows are selected, **When** the user starts the run, **Then** the confirmation counts only the selected rows, only they are sent, and the report contains only them; unselected rows do not appear in the report or in the exports.
4. **Given** a finished or stopped run in which at least one row has no output (error or "not run") or lacks a valid grade from a judge, **When** the user looks at the report, **Then** a "re-run failed requests" action is offered; when nothing failed, it is not offered.
5. **Given** the user starts "re-run failed requests", **When** the confirmation is shown, **Then** it states the number of requests per endpoint and the data sent, lists each request that will be sent on its own line (test case and part), and asks for the key(s) again; nothing is sent before the user confirms.
5a. **Given** two rows in which one judge request of one row failed and everything else succeeded, **When** the user re-runs the failed requests, **Then** exactly that one request is sent, and nothing is sent for the other judge of that row, the other row, or the main prompt.
6. **Given** a confirmed re-run of failed requests, **When** it runs, **Then** the main prompt is called only for rows without an output, and each judge only for rows whose output exists but lacks a valid grade from that judge; rows that already succeeded, and their grades, are not touched.

7a. **Given** a judge answer that was unreadable, **When** the user corrects that judge prompt and re-runs the failed requests, **Then** only the failed judge requests are sent, with the corrected prompt, and the grades that succeeded earlier are not requested again.
8. **Given** a re-run of failed requests finished, failed, or was stopped, **When** the user looks at the report, **Then** it shows the new results, the generation dates of the prompts show their latest run, and the keys used are cleared; the re-run is unavailable while a run is in progress.

### User Story 11 - An automatic audit proves that an API key is never stored (Priority: P11)

An API key must live only in the memory of the page for the time of one action and be sent only to the platform that the user chose (constitution, Principle I; FR-016). A planted copy of the key in each place is found, so "not found" means something, and the report says how much was examined in each place.

**Why this priority**: A leaked key is the one fault that the constitution calls worse than any other, and the existing checks look at a few places on the happy path only. The audit makes the promise testable in all places and under all failure modes, and it can be repeated after every change.

**Independent Test**: Run the audit: it ends with a verdict per place and per way of ending a run; then plant the fake key on purpose in a file, in the page's storage, in a cookie, in a log line, in an address, in an export, in the console, and in a header, and see each place report it.

**Acceptance Scenarios**:

1. **Given** a fake key typed into the page and used in a normal run, **When** the audit looks at the files that the run wrote or changed, the browser's own profile on disk, the log and the output of the application, the console and the exceptions of the page, the network traffic, the address and the history of the page, the storage of the page, and the downloaded exports, **Then** the key is found in none of them, except where it must be used (scenario 4).
2. **Given** the ways in which a run can end, **When** the audit repeats the examination after each of them (a normal run, a run in which the platform rejects the key and repeats it in its error message, a run that was stopped, a re-run of the judges, a re-run of the failed requests, a run abandoned by New Session, and a key that was typed but never used and the page left open), **Then** the result is the same in every one.

4. **Given** the network traffic of a run, **When** the audit reads it, **Then** the key is found only in the body of the requests from the page to the local relay, and in the authorization header of the relay's request to the platform; never in an address, a query, another header, a cookie, or a request to any other place; and the audit has first confirmed that those two uses did happen, so that the check is not empty.
5. **Given** the key written in its other forms (escaped as text in JSON, escaped for an address, encoded as base64 in each alignment, as two-byte text) and only its distinctive part (at least 12 characters), **When** the audit searches, **Then** these forms are searched in the same places, so that a partial or an encoded copy is not missed.
6. **Given** a copy of the fake key planted on purpose in each kind of place (a file in the run's folder and in the temporary folder, the page's storage, a cookie, the browser's profile, a log line, an address, an export, the console, a header), **When** the audit examines that place, **Then** it reports the copy; the audit runs these planted-copy checks as part of itself and does not trust a "not found" before they have succeeded.
7. **Given** the audit has finished, **When** its report is read, **Then** for every place it says what was examined (the number of files and bytes, requests, storage entries, console messages, snapshots), says explicitly when nothing can exist there (for example, no cookies were set), and never prints the key in full.

### Edge Cases

- What happens when the main prompt has no `{prompt_input}`, or a judge prompt lacks `{prompt_input}` or `{output}`? The run is blocked with a message naming what is missing.
- What happens when the main prompt returns an empty output? It is shown as empty; similarity is 0% unless the expected result is also empty, and the judges still judge it.
- What happens when the input is longer than the endpoint accepts? The provider's rejection is shown as a readable per-row error naming the likely cause (input too long).
- What happens when the platform stops an answer because it reached its length limit? The output is shown as received with a visible "cut off at the length limit" note, in the report and in both exports; the judges still evaluate it, and the note tells the reader why a low completeness grade may follow.
- What happens when the JSON is broken, has no `model`, or contains a reserved key? The run is blocked with a message naming the block and the problem. A parameter that is valid JSON but unknown or out of range for the platform is rejected by the platform, shown as a readable error on the row, and nothing is corrected automatically.
- What happens when the platform rejects requests for exceeding its rate limit (for example on a long dataset)? The affected rows show a readable "rate limit" error, the rest of the run continues, finished rows keep their results, and nothing is retried automatically.
- What happens when the judge endpoint rejects the key? Every judged row shows a readable error for that judge, the main-prompt outputs are kept, and the user can fix the key and re-run only the judges.
- What happens when the user changes the dataset or the main prompt after a run? The shown report keeps what it was produced with until a new run replaces it.
- What happens if the user reloads or closes the app? The session and its unexported report are lost; this is expected.
- What happens when the expected result is much longer or shorter than the output? The similarity simply reflects how much they differ.
- What happens when a judge returns a percentage outside 0–100? It is treated as an unreadable answer.
- What happens when a value contains commas, quotes, or line breaks? Quoted values and tab-separated pasted cells arrive intact; an unquoted value that breaks the column count is reported by record number and not loaded.
- What happens when the user edits the prompts after a run and then re-runs the failed requests? The main requests use the main prompt archived with the run (a changed main prompt takes effect only in a new run); the judge requests use the current judge prompts, grades that succeeded earlier are kept, and the report notes how many grades come from an earlier version of a judge prompt.
- What happens when the dataset has more than 20 rows? It loads and is previewed completely; the first 20 rows are selected by default, and the user can choose any other 20 or fewer. A run never covers more than 20 rows.
- What happens when the same row ID appears twice? The dataset is rejected before the run (see User Story 1).
- What happens when the user edits a field while the confirmation is open or while a run is in progress? While the confirmation is open the fields it describes are disabled, and a running run keeps the values it was confirmed with (FR-039).
- What happens when a judge answer carries its percentage in a slightly different form (bold label, `85/100`, a heading mark)? It is read as the grade (FR-012); a truly missing or out-of-range percentage is still an unreadable answer.
- What happens when a request is stopped between the main answer and the judges of a re-run? The row has an output and its judges are "not run", so it still counts as failed and can be completed (FR-040).
- What happens when the user types something that looks like a platform key into the parameters JSON? The JSON is used as written, but in the report and in the exports that text is replaced by `[key]` (FR-045), because the exports must never contain a key.
- What happens when the platform answers with an extremely large body? The answer is refused with a readable "answer too large" error on that row, instead of exhausting the memory of the computer (FR-046).
- What happens on a window that is resized during a run or a confirmation? The layout follows the width at once; the lock, the progress, and the run panel keep their state.
- What happens with a very long model name or endpoint in the chips and the run panel? The text wraps or is shortened with its full value available (title or expandable), and never widens the page.
- What happens when a dataset has many rows? The preview scrolls inside its card with the column headings kept in view; the header chip counts selected rows only.
- What happens to the readiness list while a step is not unlocked yet? Its problems are listed in a dimmed group with the note when it becomes available, and as soon as the step unlocks the group becomes normal.
- What happens to the bottom bar when a confirmation is open? The panel with the confirmation comes into view, the bar shows that a confirmation is waiting, and its action is disabled, as Run is while the form is locked.
- What happens when the readiness list has many problems? It shows all of them in a list that scrolls inside the panel; the number of problems is also shown on the step indicator.
- What happens when the computer has no browser, or the browser cannot be driven? The command says so in one plain sentence, runs nothing else, and exits with its own status (not the one of a failed check).
- What happens when a check hangs? It is stopped after its own time limit, reported as failed with the screenshot at that moment, and the run goes on.
- What happens when the dark appearance cannot be requested from the browser? The checks of that appearance are reported as "not run" with the reason; the run does not pass silently.
- What happens to the files of a run? They go to a folder named after the date and time of the run, hold only the fake key (never a real one), and are never read back by the application.
- What happens when the browser writes its storage with a delay? The audit closes the browser properly (so that it flushes what it keeps) before it reads the profile on disk, and only then removes the profile.
- What happens with a file that is too large or not text? Files are searched as bytes; a file above the size limit of the audit is listed as skipped with its size, never silently passed over.
- What happens when a memory snapshot cannot be taken? That part is reported as "not run" with the reason, not as a pass.
- What happens with places outside the audit's reach (the user's own terminal and shell history, swap files of the operating system, the memory of other programs, the platform's own storage)? They are listed as out of scope in the report; the audit makes no claim about them.
- What happens when the user presses the re-run action while it is unavailable? Nothing is sent; the one line next to it says why (FR-076).
- What happens when New Session is pressed while a run is in progress? After the confirmation the run is stopped, requests already sent are not waited for, no further request is sent, the answers that arrive later are dropped, and the new session starts empty (FR-077).

## Requirements *(mandatory)*

### Functional Requirements

**Session**

- **FR-001**: The app MUST open on a start screen offering one action, New Session, and MUST keep all further steps unavailable until it is pressed. It MUST state that a session's content lives in memory only and is lost when the session ends or the app is reloaded.
- **FR-002**: Pressing New Session while a session holds a dataset or results MUST require confirmation that warns about unexported results and then start an empty session.

**Dataset**

- **FR-003**: The app MUST let the user load a dataset by choosing a file or by pasting its text, in the fixed format with the columns `id`, `name`, `prompt_input`, and `expected_result` (header row, names matched ignoring letter case). Other columns are not used. The separator between columns MUST be detected automatically from the header row among tab, semicolon, and comma, so that text copied from a spreadsheet (tab-separated) and files saved by common spreadsheet programs (often semicolon-separated in Polish settings) load without conversion. A value that contains the separator, a double quote, or a line break MUST be accepted when wrapped in double quotes (a double quote inside it written doubled); a double quote in the middle of an unquoted value MUST be kept as ordinary text. Header names MAY be wrapped in double quotes, and the line breaks of the data MAY be of the Windows (CR+LF), Unix (LF), or old Mac (CR alone) kind.
- **FR-004**: The app MUST validate the data when loaded and show a preview, and MUST report with a specific, readable message: missing columns, empty or duplicate IDs, empty names, empty prompt inputs, and unreadable, malformed, or empty data. No run may start with such errors. A record with a number of columns different from the header MUST be reported by its number together with the likely cause (for example, a value containing the separator that is not wrapped in double quotes), and the data MUST NOT be loaded partially. A double-quoted value that is still open at the end of the data MUST be reported as an error naming the record in which the quote was opened; no later record may be absorbed into it.
- **FR-005**: A row with an empty expected result MUST be flagged and MUST remain runnable, with its similarity shown as "no expected result".
- **FR-006**: Values MUST support long multi-line text of at least 100,000 characters, preserving line breaks; in the dataset preview they MUST be shown shortened with their length and expandable, in the report in a box that scrolls inside itself (FR-023), and they MUST be sent complete.

**Main prompt**

- **FR-007**: The app MUST show the main prompt as one editable text with the single data place `{prompt_input}`, highlighted inside the text without relying on color alone, and MUST show below it an example of the complete prompt for a row of the dataset (the first by default, changeable), with the inserted value highlighted and updated as the user types.
- **FR-008**: The app MUST block the run when the main prompt lacks `{prompt_input}` or contains any other word in single curly braces, naming the problem. A literal brace MUST be writable by doubling it. Every occurrence of `{prompt_input}` receives the same value for a row.

**Judges**

- **FR-009**: The app MUST provide exactly two judges, Accuracy and Completeness, each with one editable prompt that is pre-filled with a ready-made version.
- **FR-010**: A judge prompt MUST use the places `{prompt_input}` (the row's input data) and `{output}` (the main prompt's output for that row), highlighted without relying on color alone. The run MUST be blocked, naming the judge and the problem, when either place is missing or when another word in single curly braces is used. A preview of the full judge input for a chosen row MUST be shown, with a clearly marked stand-in for the output before one exists.
- **FR-011**: The app itself MUST instruct each judge to answer with a percentage from 0 to 100 and a rationale; the user does not write the answer format.
- **FR-012**: An answer without a usable percentage (missing, not a number, outside 0–100) MUST be shown as an "unreadable answer" error with the raw text and left out of that judge's average. The percentage MAY be written with a percent sign or as "n/100", and the line that carries it MAY be wrapped in bold or other emphasis marks or begin with a heading mark (for example `**SCORE:** 85`, `SCORE: 85/100`, `## SCORE: 85%`); the last such line counts.
- **FR-031**: The ready-made Accuracy prompt MUST instruct the judge, as a QA reviewer, to extract every verifiable fact from `{output}`, check each only against `{prompt_input}` (no outside knowledge), give each fact a verdict (correct, incorrect with the correct value, or unsupported), accept rounding, not penalise omissions, and report the list of facts with verdicts and an overall accuracy percentage. The ready-made Completeness prompt MUST instruct the judge, as a QA reviewer, to list every fact of `{prompt_input}`, check whether each appears in `{output}` with the same value (a wrong value counts as present, with a note), and report the facts that appear, the facts that are missing, and an overall completeness percentage. The lists MUST be part of the judge's rationale shown in the report.
- **FR-013**: The page MUST state that the judges add one request per judge per row and may cost extra.

**Configuration**

- **FR-014**: The page MUST show a configuration. The Main prompt block MUST have an endpoint address (pre-filled with the test platform's address), an API key, and one JSON field holding the model and its parameters (the model is the `model` key of the JSON; there is no separate model field). The LLM as Judge part MUST have the option "Same model as the main prompt", on by default; while it is on, the judges MUST use the main prompt's endpoint, key, and JSON and no judge fields MUST be shown; while it is off, the judge part MUST show its own endpoint, API key, and JSON field, shared by both judges. The JSON fields MUST be pre-filled (main prompt: the default model; judge part: the second known model, see Assumptions). No other option exists.
- **FR-015**: The app MUST block the run, naming the block and the field, when a shown endpoint is empty or not a well-formed http or https address, or a shown key is empty. The same endpoint, key, or JSON MAY be used in both blocks.
- **FR-030**: Each shown JSON field MUST be checked before a run: it MUST be valid JSON, MUST be an object, MUST contain a non-empty text under `model`, and MUST NOT contain the keys `messages` or `stream`; otherwise the run MUST be blocked with a message naming the block and the problem. A valid JSON MUST be added to the request as written, without further interpretation or range checks, and MUST be recorded in the report (for the judges, either their JSON or a note that they used the main prompt's).
- **FR-016**: Keys MUST be masked when entered, MUST NOT be persisted to any database, file, log, or browser storage, MUST be held only in volatile memory, and MUST be cleared from memory and screen when the run, judge re-run, or re-run of failed requests that needed them finishes, fails, or is stopped. Keys MUST NOT appear in URLs, error messages, or the exports. This applies to every component that handles a request, including any intermediary used to reach the endpoint: it MUST NOT store or log keys, prompts, or answers, and MUST use them only to pass the request on. After that moment no copy of a key MAY remain reachable in the application's memory (for example inside the means used to stop or continue a run), and a run that was abandoned by New Session MUST NOT clear, fill, or otherwise change the keys or the progress of the new session.

**Run**

- **FR-017**: Before a run, the app MUST state how many requests go to each endpoint, to which model, and what data goes to each, and, when requests pass through an intermediary of the app, MUST say so. It MUST send nothing until the user confirms. Nothing is sent as a side effect of editing, loading, or navigating.
- **FR-018**: The run MUST be performed in two phases: the main prompt on every selected row first, then the judges on the rows that have an output. Progress MUST be shown for each phase.
- **FR-019**: If the platform reports that an answer was cut off at its length limit, the row MUST show the output with a visible note saying so. A failure of the main prompt on a row MUST be shown as a readable error on that row, MUST NOT stop other rows, and MUST prevent judge calls for that row ("nothing to judge"). A failure of one judge on a row MUST NOT affect the other judge or other rows.
- **FR-020**: The user MUST be able to stop a run; afterward no further requests are sent, finished rows keep their results, and unfinished rows are marked "not run".
- **FR-021**: The expected result MUST NOT be sent to either endpoint.

**Report**

- **FR-022**: The result MUST be shown as an HTML report. At its very top it MUST contain the header and the cards with the averages of FR-037, then the summary table of FR-032, then the table of the prompts used of FR-033, followed by the main prompt and both judge prompts exactly as used by the run, for archiving, in a section that is **collapsed by default** (opened with one click) so that the results stay near the top. The model and the parameters are shown once, in the table of FR-033, and are not repeated in the archive.
- **FR-023**: Below the prompts, the report MUST show the results in one table in which **every row of the run (test case) takes its own lines, one test case under the other** (never one column per test case: the table must not become wider as the number of test cases grows). A test case consists of: a heading line with the test case (ID and name); the **main prompt line** with these fields side by side, in this order: prompt input (its own wide column, showing the text in a box of limited height that scrolls inside itself, never collapsed behind a toggle, with its length in characters), expected result, actual output, similarity to expected output (%), differences; and the **judge line** below it, in which the metrics are one under the other (Accuracy, then Completeness), each with its grade and its rationale. The report uses the full width of the window (FR-038). The heading line of a test case (ID and name) is the first line of its group, **above** the column headings of its main prompt line, so that every test case reads from top to bottom as: who it is, what the columns are, then the values. **Every long text of a test case is shown the same way as the prompt input: in full, in a box of limited height that scrolls inside itself (reachable with the keyboard, can be resized vertically), never collapsed or cut off**; this applies to the prompt input, expected result, actual output, differences (about 17 lines) and to the rationales of the judges (about 9 lines). A short text takes only the space it needs, so a box appears only when the text is longer than the limit, and one very long text never makes the whole row taller than the limit. The *differences* field shows the actual output as one text in which the words that exist only in the expected result are struck through and the words that exist only in the actual output are marked as added (words, not characters; the marks differ by more than color); with no expected result or no output it shows that instead. The expected result MUST be shown in full (not collapsed); a row without an expected result MUST show that. Errors and "not run" states MUST appear in place of the missing fields. On a window narrower than about 900 px the fields of the main prompt line MUST be shown one under the other, each across the full width with its own label (the column headings line is then replaced by those labels), so that the report is never wider than the window and no horizontal scrolling of the page is needed.
- **FR-024**: The similarity MUST be a percentage computed by the app from the actual and the expected text, without any model call, as a character-level similarity: after removing surrounding whitespace from both texts, it is 100% minus the share that the edit distance (the smallest number of single-character insertions, deletions, or replacements that turns one text into the other) makes of the length of the longer text, rounded to a whole percent. The comparison is case-sensitive. Two empty texts give 100%; one empty text gives 0%. For example, "abcd" and "abce" give 75%, and identical texts give 100%.
- **FR-025**: The report MUST show the average grade of each judge and the average similarity, counting only rows that have a value, both in the average cards at the top (FR-037) and in the last line of the summary table; the two MUST show the same numbers.
- **FR-032**: At the very top of the report, before the prompts, the app MUST show a compact summary table with one line per row of the run: the test case (ID and name, linked to that row's lines in the results table), the similarity (%), the Accuracy score (%), and the Completeness score (%), and a final line with the average of each of the three values over the rows that have one. A row that failed, was not run, was not judged, or has no expected result MUST show that state in place of the missing value. The table MUST be part of the HTML export; the CSV export keeps its one line per row.
- **FR-033**: Right below the summary table (FR-032) the report MUST show a table with one line for the main prompt and one for each judge, giving: the model used, the request parameters used (the JSON of that configuration without the `model` key, as a short list of names and values), and the date and time at which the results of that prompt were generated. For the judges, the date and time MUST be that of their latest run (a re-run updates it); for the main prompt, that of its run. The date and time at which the report itself was produced MUST be shown above the tables. Dates and times are local time as `YYYY-MM-DD HH:MM:SS` (the UTC offset is shown once in the report header); in the CSV they are ISO 8601 with the UTC offset. All of this MUST be part of the HTML export; the CSV export MUST add, to each line, the parameters used and the generation date and time of the main prompt and of the judges.
- **FR-026**: The user MUST be able to export the result of a finished or stopped run in two formats. **HTML**: a single self-contained file that opens without the app and holds everything shown in the report (the three prompts, the rows, the averages). **CSV**: a file with a header row and one line per row of the run, with the report fields as columns in the same order (the expected result right after the actual output) and an error/state column ("ok", the readable error, or "not run"). Both exports MUST leave out all API keys and endpoints, and the CSV MUST escape commas, quotes, and line breaks, and open correctly in common spreadsheet programs including Polish characters. In the CSV, a text value that begins with `=`, `+`, `-`, `@`, a tab, or a carriage return MUST be written with a leading single quote (`'`), so that a spreadsheet program shows it as text and never evaluates it as a formula; the numeric columns (similarity and grades) are not changed, and the HTML export is not affected.

**Judge re-run**

- **FR-027**: After a run, the user MUST be able to re-run only the judges. This MUST call only the judges, only for rows that have an output, with the current judge prompts and endpoint, MUST NOT send any request to the main endpoint, and MUST NOT change outputs, errors, or similarities.
- **FR-028**: A re-run MUST disclose the number of judge requests and the data sent (FR-017), ask for the judge key again, show the previous grade next to a changed one, be stoppable (finished rows keep new grades, the rest keep previous ones), and be unavailable while a run is in progress; its confirmation MUST also say that "Re-run failed requests" repeats only the requests that ended with an error.

**Row selection and re-run of failed requests**

- **FR-034**: The dataset preview MUST show a check box per row, with "select all" and "select none" and the number of selected rows next to the limit. All rows MUST be selected by default, or the first 20 when the dataset has more than 20 rows. A run MUST cover from 1 to 20 selected rows and MUST be blocked, with a message giving the current count, when none or more than 20 are selected. The dataset itself MAY have more than 20 rows. A run, its confirmation (FR-017), its report, and its exports MUST cover only the selected rows.
- **FR-035**: After a finished or stopped run, when at least one row has no output (error or "not run") or lacks a valid grade from a judge, the app MUST make the failed requests repeatable by the choices "Re-run failing main prompts and all related judges" and "Re-run only the failing judges" of FR-075 (visible at all times and unavailable otherwise, FR-076; in this text "re-run failed requests" means these two choices together). It MUST disclose the number of requests per endpoint and the data sent, ask for the key(s) again, and send nothing before confirmation (FR-017). The confirmation MUST list **every request that will be sent, one line each** (the test case and the part: main prompt, Accuracy, or Completeness), and the number of lines MUST equal the number of requests, so that the user can see that nothing that already succeeded is repeated. It MUST call the main prompt only for rows without an output and each judge only for rows whose output exists but lacks a valid grade from that judge, MUST NOT change rows that already succeeded, MUST use the main prompt, the model, the parameters, and the "Same model as the main prompt" choice archived with the run, MUST use for the judge requests the **current text of the judge prompts** (so that a judge prompt that was corrected after an unreadable answer takes effect; the model and the parameters of the judges stay those archived), MUST keep the grades that already succeeded as they are, MUST take the endpoint addresses and the keys from the current configuration (the keys are asked for again), and MUST clear the keys when it finishes, fails, or is stopped. The generation dates of FR-033 MUST show the latest run of each prompt. When the text of a judge prompt used for the re-run differs from the one behind grades that were kept, the report MUST say so: the line of that judge in the prompts table of FR-033 notes how many grades come from an earlier version of the prompt, and the archive of FR-022 lists that earlier version too (labelled with the number of grades it stands behind).

**Language**

- **FR-038**: The report MUST be shown in its own **view that uses the full width of the window** (FR-023, FR-037) and replaces steps 1–4 while it is open; the view MUST open by itself when a run, a judge re-run, or a re-run of failed requests finishes or is stopped, and step 5 MUST offer an "Open report" action that opens it at any time (also during a run, showing the results received so far). **Audit that a key is never stored (User Story 11)**

- **FR-066**: One command MUST run the audit (also available as a group of the acceptance walk-through), with a fake key that is unique to each run and clearly recognisable; it MUST NOT contact the real platform and MUST need no key and no internet access, and MUST finish within 3 minutes.
- **FR-067**: The audit MUST examine, after each way of ending a run (FR-068): (a) every file written or changed during the run in the project, the run's folder, and the temporary folder of the computer; (b) the browser's own profile on disk, read after the browser was closed properly; (c) the log and the output of the application's process; (d) the console messages and exceptions of the page; (e) all network traffic of the page (addresses, headers, bodies); (f) the address of the page, its history, and its cookies; (g) the storage of the page (local, session, databases, caches); (h) the exports; (i) the fields and the text of the page.
- **FR-068**: The audit MUST repeat the examination for each of these ways of ending a run: a normal run; a run in which the platform rejects the key and repeats it in its error message; a stopped run; a re-run of the judges only; a re-run of the failed requests; a run abandoned by New Session; and a key that was typed but never used, with the page left open.
- **FR-069**: The audit MUST search for the whole key and for its distinctive part (at least 12 consecutive characters), as plain text, escaped for JSON, escaped for an address, encoded as base64 (in each of the three alignments), and as two-byte text (in the platform's answer, only the whole key is searched for, FR-074).
- **FR-070**: The key MAY appear only in the body of the requests from the page to the local relay and in the authorization header of the relay's request to the platform; the audit MUST confirm that both uses happened (so that the examination is not empty), and MUST report any other occurrence, with the place and a masked excerpt.
- **FR-071**: After each way of ending a run, the audit MUST take a snapshot of the memory of the page and of the memory of the application's own process and MUST report any reachable string that holds the key or its distinctive part (FR-016: no copy of a key may remain reachable), and MUST check that the key fields of the page are empty.
- **FR-072**: Before it trusts a "not found", the audit MUST prove that it can see a key: it plants a copy of the fake key in each kind of place of FR-067 (as far as the place can be written to, and for the memory by holding it in a variable of the page and in the process), and each planted copy MUST be reported; a place whose planted copy was not found makes the audit fail.
- **FR-073**: The audit's report MUST give, per place and per way of ending a run, a verdict and what was examined (counts of files and bytes, requests, entries, messages, snapshots), MUST state when nothing can exist in a place, MUST list what is out of scope, MUST list skipped files with the reason, and MUST NOT contain the key in full (an excerpt is masked); the run's folder is searched for the key at the end, as for the acceptance walk-through (SC-035).
- **FR-074**: The answer that the app passes from the platform back to the page MUST NOT contain the API key: if the platform repeats the whole key in its answer or its error message, in plain text, escaped for JSON, escaped for an address, or encoded as base64 (the forms that the audit searches for, FR-069, except the distinctive part alone), the key is removed from the answer before the page receives it, so that the key is present in the traffic only in the two permitted uses (FR-068) and the page shows a readable error without it. The audit applies this requirement to the whole key in the forms listed here; a bare piece of the key (FR-069) is searched for in every other place, but is not expected to be removed from the platform's answer.

**Re-run choices and New Session (User Story 12)**
- **FR-075**: The app MUST offer one re-run control with four choices, named in the interface as follows. (1) "Re-run all": the main prompt and then the judges on the rows of the last run, with the settings now on the form, as pressing Run does. (2) "Re-run failing main prompts and all related judges": for each row without an output (error or "not run") the main request and then both judges. (3) "Re-run all judges": both judges on every row that has an output, with the current judge prompts and endpoint, no request to the main endpoint, no change of outputs, errors, or similarities (this is the behavior of FR-027). (4) "Re-run only the failing judges": a judge request for each row that has an output and lacks a valid grade from that judge, and nothing else. Choices (2) and (4) never overlap, and together they send exactly what "Re-run failed requests" of FR-035 sent; their rules (the definition of a failed request in FR-035 and FR-040, the archived main prompt, model, and parameters, the current judge prompts, the itemised confirmation with one line per request, grades that succeeded kept as they are) apply unchanged. For a run of 10 rows in which one judge request failed, choice (4) MUST send exactly one request and change no other result. Every choice MUST disclose the number of requests per endpoint and the data sent, ask for the key(s) again, send nothing before confirmation (FR-017), be stoppable, and clear the keys when it finishes, fails, or is stopped (FR-016, FR-028).
- **FR-076**: The re-run control MUST be visible at all times in the run panel and in the toolbar of the report, with the same label and choices. Each choice MUST show the number of requests it would send, and MUST be available only when a run has ended or been stopped and the choice has something to send; otherwise it MUST be shown as unavailable with one short line that says why ("A run is in progress", "No run yet", "Nothing failed", "No row has an output", or "The rows of the last run are no longer loaded"). Choosing one from the report MUST lead to the form with the keys to be entered and the confirmation of FR-017. This replaces the separate placement of "Re-run judges only" (FR-027, FR-043) and "Re-run failed requests" (FR-035) and the rule that offers them only at certain moments.
- **FR-077**: Once a session has started, exactly one New Session button MUST be visible in the header band on every screen, including the report and a run in progress. Pressing it MUST follow FR-002 (confirmation that warns about unexported results), and after the confirmation MUST close and remove the report, the dataset, the results, the exports' source data, and the keys, MUST stop a run in progress without sending anything further and drop answers that arrive later (User Story 8 scenario 12), and MUST leave an empty session. Cancelling MUST change nothing and return the focus to the button.

**Privacy**

- **FR-029**: The app MUST NOT persist the dataset, prompts, endpoints, or results beyond the open session; they leave it only through an explicit export (HTML or CSV). While results exist that were not exported since their last change, closing or reloading the page MUST ask the browser for confirmation (nothing is stored to support this).

### Key Entities

- **Session**: Started by New Session; holds the dataset, the row selection, the three prompts, the configuration, and the report; kept in memory only.
- **Dataset row (scenario)**: ID, name, prompt input, expected result.
- **Main Prompt**: The editable text with `{prompt_input}`.
- **Judge Prompt** (Accuracy, Completeness): An editable text with `{prompt_input}` and `{output}`; returns a percentage and a rationale.
- **Configuration**: The Main prompt block (endpoint address, API key, one JSON with the model and its parameters) and the LLM as Judge part (the option "Same model as the main prompt", on by default; when off, its own endpoint, API key, and JSON shared by both judges). Keys are held only temporarily.
- **Row Result**: ID, scenario, prompt input, actual output, expected result, similarity (%), and per judge a grade and a rationale; or an error or "not run" state.
- **Report**: The HTML result: the three prompts used, the row results, and the averages; can be exported as one HTML file, and its rows as a CSV file.

## Assumptions

- Single-user tool with no accounts or saved libraries. A session is started by pressing New Session and lives only in memory; the exported HTML or CSV file is the only way anything leaves the app.
- The dataset format is fixed: four columns (`id`, `name`, `prompt_input`, `expected_result`). There is exactly one data place in the main prompt, `{prompt_input}`; splitting data into several parts is out of scope. The expected result is exact text.
- The page offers a sample dataset (one real country table and some clearly marked invented examples) so that the whole flow can be tried without preparing any data.
- **Typical dataset row**: one country, with the whole Eurostat "Selected indicators" table as `prompt_input` (about 18 indicators, tab-separated text over many lines, around 1.6 thousand characters; the name, the unit in brackets, the value and the period in brackets, and "View source data" repeated per indicator), the country as `name`, and a summary text as `expected_result`. Each country is a separate row (for example Poland, Czechia); the data is not split into areas.
- Loading by pasting means pasting the dataset text in the same table format as a file. The most reliable way to paste values with commas, quotes, or line breaks is to copy the cells from a spreadsheet (tab-separated, no quoting needed); text typed by hand with commas inside values must wrap those values in double quotes. The app does not guess where a value ends when quoting is missing; it reports the record instead.
- The "similarity to expected output" is the character-level similarity defined in FR-024. It is a measure of how much the two texts differ in characters, not of meaning: two correct summaries worded differently can score well below 100%, and a reordered text scores lower than a word-by-word comparison would give. The judges give the meaning-based signal.
- The judges are language-model based. Their grades are percentages from 0 to 100 produced by the judge following its prompt; the app does not compute grades itself and does not guarantee their correctness. The ready-made prompts are suggestions that the user can edit.
- The judges compare the output with the row's input data (`{prompt_input}`); using the expected result inside judge prompts is not offered in this version.
- "Endpoint" means an address the app calls with the prompt text and a key. The model and all request parameters are one JSON text per configuration block, described in the next points.
- **Test platform**: the user's test platform is the set of models hosted by NVIDIA and reached through its API. The access contract (confirmed by the user's sample call) is collected in `references/nvidia-hosted-models-api.md`. In short: a chat-style, OpenAI-compatible request is sent to the fixed hosted address, the personal API key (obtained by free sign-up through the NVIDIA Developer Program) is sent as a bearer credential, the model is named by an identifier such as `nvidia/nemotron-3.5-bolt-e4b`, and the answer text is read from the first choice of the response (`message.content`; the platform returns the reasoning trace in a separate field, `reasoning_content`, which is not part of the output). Nothing else in this specification depends on the provider, and any endpoint with the same request format can be used.
- **What a request contains**: a single user message with the resolved prompt text (the main prompt with its value inserted, or the judge prompt with its two values inserted, plus the answer-format instruction for judges). The app sends no system message and no tools, and does not use streaming, because it needs the complete answer. A reasoning trace that the model may produce is not part of the output. The request parameters (for example temperature, top_p, answer length limit, reasoning options, seed) are taken as written from the model's Parameters JSON, pre-filled from the default parameters below; the app adds only the message and non-streaming mode.
- **Where the app runs**: locally on the user's own computer, for one person. Nothing is hosted for others in this version, so no key, prompt, or answer passes through a shared server.
- **Reaching the platform from the app**: reports from other developers indicate that the platform's hosted API accepts calls from web pages only when they originate from NVIDIA's own sites, so a page that talks to it directly from the browser may be blocked. If that is confirmed at planning, requests are passed through an intermediary of the app, which runs on the same local computer as the app. The behavior in this specification does not change, but the intermediary is bound by FR-016: it never stores or logs keys, prompts, or answers, and the consent statement (FR-017) names it as part of the path.
- **Platform limits**: the free tier is reported to allow roughly 40 requests per minute and a model context of up to about 64K tokens (varies by model; unverified). The app therefore may pace requests, at a rate chosen at planning, but never retries on its own: a request rejected for rate or length reasons is shown as a readable error on its row, and the user can start a new run.
- Both judges always use the same model, endpoint, key, and parameters: by default those of the main prompt, or, when the user switches "Same model as the main prompt" off, one separate set for both judges. Different models for Accuracy and for Completeness, saved endpoint lists, and endpoint names are out of scope.
- **Default JSON**: both fields are pre-filled so that the models run as they are, taken from the platform's sample calls. The main prompt's field starts with the default model; the judge fields (shown only when the option is off) start with the second known model. They are filled in when the session starts and stay as the user leaves them.
  - Main prompt (`nvidia/nemotron-3.5-bolt-e4b`): `{"model":"nvidia/nemotron-3.5-bolt-e4b","temperature":1,"top_p":0.95,"max_tokens":4096,"seed":42,"chat_template_kwargs":{"enable_thinking":true}}` (the sample call uses 1024 as the answer length; raised to 4096 so that a summary, or a judge's answer after its reasoning, is not cut off; a live check at planning confirmed that a judge answer finishes normally with this value, long real summaries are to be seen in the first real run).
  - Judges, when set apart (`nvidia/nemotron-3.5-lightning-30b-a3b`): `{"model":"nvidia/nemotron-3.5-lightning-30b-a3b","temperature":1,"top_p":0.95,"max_tokens":16384,"reasoning_budget":16384,"chat_template_kwargs":{"enable_thinking":true}}`.
  - The request fields the app sets itself are `messages` and a non-streaming mode.
- **Second model**: `nvidia/nemotron-3.5-lightning-30b-a3b` is a larger NVIDIA-hosted model offered for the judges when the user wants them to use a different model than the main prompt. Its sample call (see `references/nvidia-hosted-models-api.md`) uses the same address and bearer key, a much larger answer limit (16384 tokens) and a separate reasoning-budget setting. Its default JSON is above.
- The result is shown as an HTML report and can be exported as HTML (for archiving, since it also holds the three prompts used) and as CSV (for analysis in a spreadsheet; one line per row, without the prompts and without the averages). Neither export contains endpoints or keys.
- Only the latest run is shown; a new run replaces it. Comparison of runs, a history of judge runs, manual entry of outputs or grades, further judges, and a combined final grade are out of scope.
- **Data volume**: a run covers at most 20 rows (60 requests: one main-prompt request and two judge requests per row), which at the platform's reported free limit of about 40 requests a minute takes roughly two minutes. Larger datasets are handled by choosing rows (User Story 7) and running several times; a bigger limit is out of scope for this version.
- Rows are processed in any order and with any concurrency inside each phase, as long as progress is shown and a stop halts further requests promptly.
- **Language**: the whole interface and report are in English (FR-036), including the start button "New Session"; the quotation of the original request at the top of this specification stays in Polish as written by the user. Dataset content and typed prompts may be in any language.
- The project constitution (v1.0.0) rules on keys, consent before sending data, readable errors, and no persistence apply.
- **Code review of 2026-11-01**: an independent review of the finished application produced the corrections of User Story 8 (FR-039 – FR-047 and the amendments to FR-003, FR-004, FR-012, FR-016, FR-026, FR-038). Default chosen without asking, which the user may change: the limit for an answer of the platform is 8 MB (a chat answer is far smaller). Out of scope: judging whether the user typed a key into the parameters JSON on purpose (the text is only hidden in the report and the exports), and any change of the Node version required by the application.
- `example-report-modern.html` and `example-form-modern.html` in this folder are the references for the appearance of the report (FR-037) and of the application page (FR-048 – FR-057), with simulated data; in every other respect this specification takes precedence.
- **Modern look of the application page (User Story 9)**: the user is open to negotiating the arrangement of the fields, the place of the buttons, and the animations. The arrangement written above is the one shown on the reference page [example-form-modern.html](example-form-modern.html) (simulated data, not the application): a header band with chips, a step indicator under it, the steps as cards in one column, and a run panel beside them on wide windows that stays in view (readiness list, counts, Run, Stop, progress, confirmation, result actions), subtle transitions of at most 250 ms. The user accepted the reference page, which settles the points that were open: the run panel stands at the side on wide windows, the step indicator is horizontal under the header band, and the motion is subtle. Out of scope: a manual switch between light and dark (the system setting decides), user-resizable panels, saved layouts, logos or other branding, and charts other than the existing gauges and bars.
- **Automated acceptance walk-through (User Story 10)**: a development tool, not a part of the application's screens; it ships in the repository next to the tests and is started from the command line. It needs the same browser that the end-to-end scenarios already use (Chrome or Chromium) and no new dependency. The scripts-level end-to-end scenarios stay (they are fast and run in the unit-test command); the walk-through adds what they cannot see: real input, real downloads, the system's dark and reduced-motion settings, and screenshots. It does not replace the live check with a real key. Out of scope: other browsers (Firefox, Safari), automated judgment of how professional the page looks, and running against the real platform.
- **Audit that a key is never stored (User Story 11)**: a development tool that extends the acceptance walk-through and reuses its browser driver, its fake platform, and its run folder; it needs the same browser and adds no dependency. The browser's own profile is a fresh temporary one, so the audit says nothing about the user's everyday browser (its password manager, its autofill, its extensions), which it cannot see; the page does not submit a form, so a browser has nothing to offer to save. The memory of the application's process is examined through the debugging connection that the runtime itself offers, in a separate instance started for the audit (the instance used for the rest of the walk-through is the real command, unchanged). Out of scope: the user's terminal, shell history, and clipboard; swap files and crash dumps of the operating system; other programs; and everything on the platform's side.
- **Re-run choices and New Session (User Story 12)**: the behavior behind "re-run failed requests" (which requests are failed, what is sent, which prompts are used) is unchanged and is now reached through two of the four choices; this story changes where the choices are, how they are named, and when they are shown. "Re-run all" is the same as pressing Run for the rows of the last run and uses the settings on the form now. "Visible during the run" means visible but unavailable, because two runs at the same time on the same rows would give unreadable results. If rows with failed main requests and rows with failed judges exist at the same time, the user chooses the two failing-only choices one after the other; a single choice for both was not asked for. New Session keeps its confirmation when there is something to lose (FR-002), because pressing it clears the report and unexported results cannot be brought back.
